Engenharia de Requisitos: O Contrato do Software

Capturando a intencionalidade: o que o sistema faz vs como ele deve se comportar sob carga.

Requisitos são as restrições e funções que guiam a construção do software. Um sistema que faz tudo o que foi pedido (requisitos funcionais) mas cai com 10 usuários simultâneos (requisitos não funcionais) é um **fracasso de engenharia**.

1. Requisitos Funcionais (FR): O "O Quê"

FRs descrevem as interações entre o sistema e seu ambiente. São declarações de comportamentos: *"O sistema deve permitir que o usuário cancele um pedido antes do faturamento."*

graph LR U[Usuário] -- Comanda --> S[Sistema] S -- Evento --> D[Domínio] D -- Resposta --> U Note over S: RF: Validar Estoque Note over D: RF: Registrar Pedido

2. Requisitos Não Funcionais (NFR): O "Como"

NFRs definem as qualidades do sistema: performance, escalabilidade, segurança e confiabilidade. Em engenharia, costumamos falar em **Disponibilidade (SLA)**.

$$A = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}}$$

Onde \(MTBF\) é o tempo médio entre falhas e \(MTTR\) é o tempo médio de reparo. Se queremos "Cinco Noves" (99.999%), o tempo de inatividade permitido é de ~5 minutos por ano.

A Regra dos Acordos (SLA vs SLO vs SLI)

Engenheiros de SRE usam méricas rigorosas para garantir NFRs:

  • SLI (Indicator): A métrica real (ex: Latência).
  • SLO (Objective): A meta (ex: 95% das requests < 300ms).
  • SLA (Agreement): O contrato legal (ex: Devolvemos dinheiro se cair por > 1h).

Conclusão

A Engenharia de Software é a arte de equilibrar FRs ambiciosos com NFRs realistas. Documentar requisitos não é burocracia, é a criação do **blueprint** de sucesso do projeto.
